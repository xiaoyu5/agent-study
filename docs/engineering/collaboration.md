# Lead / Develop 协作规范

状态：项目协作基线草案。Lead 由用户个人与 AI 共同承担；Develop 为一个或多个 AI。
本规范约束开发团队，产品内部是否采用多个 Agent 是独立架构决策。

## 1. 角色与决定权

| 角色 | 主要责任 | 审核证据 |
| --- | --- | --- |
| 人类 Lead | 确定学习者、课程目标与范围；审核学习价值、内容适用性和重要取舍 | 任务或批次批准记录、决策结论及适用范围 |
| Lead AI | 拆任务、先定共享接口、安排依赖；独立检查实现、验证结果与架构一致性 | 待合并 SHA、技术审查结论、问题处置与验收证据 |
| Develop AI | 在授权范围实现、自检、解释设计、记录失败和交接 | 提交、实际执行的命令与结果、未解决问题 |

Lead AI 可参与实现，但自己编写的变更须由另一 AI 审查者或人类完成独立技术复核。
Develop 可自主决定任务内可逆的实现细节；不得自行批准重大需求、课程目标或评测标准变更。
已批准的范围和操作授权持续有效，不为编辑、调试、读取资料等常规步骤逐项询问。
遇到新的重要取舍，先完成不受影响的工作并给出具体选项、影响与建议，再提交 Lead 决策。

## 2. 从学习目标到任务

每个里程碑按“原理解释 → 小练习 → 项目实现 → 验收 → 复盘”推进。
首课为概率与决策／贝叶斯思维；以 Python 实现，先交付本地课程查看与校验骨架。
模型调用、工具循环和学习过程编排进入后续任务，不提前宣称已有教学效果或完整 Agent 能力。
验收要区分软件能否正确运行与学习者能否理解、解释、迁移应用；两类证据分别记录。

任务卡至少包含以下字段，可放入仓库文档或任务系统，保持一个可引用的权威版本：

```yaml
id: edu-xxx
title: 一句话描述可验收结果
status: proposed
learning_goal: 本次理解或练习的原理
user_outcome: 对学习者产生的具体结果
scope: 包含项与非目标
acceptance: 可观察的验收条件及样例
owner: Develop AI 标识
reviewers: 人类 Lead 与 Lead AI 标识
branch_worktree: 分支、绝对路径、基线 SHA
allowed_paths: 允许写入的路径
dependencies: 前置任务及接口版本
validation: 实际可执行的命令、工作目录及环境
versions: 课程、rubric、评测集等适用版本
decisions: 已批准需求与重要取舍的记录链接
handoff: 交接记录链接
```

## 3. 状态与完成定义

`proposed → ready → in_progress → ready_for_review → in_review → done`

- `proposed`：提出目标与范围，尚未具备开发条件。
- `ready`：Lead 已确定验收、接口和依赖；AI 可领取并在范围内执行。
- `in_progress`：指定 Develop 正在实现、自检，记录阻塞与范围变化。
- `ready_for_review`：实现与自检完成，提交和交接材料齐全；这不等于已批准或已交付。
- `in_review`：Lead 已开始审查；需要修改则回到 `in_progress`。
- `done`：具备两类 Lead 审核证据、已合并 `main`、主干验收通过、交接完成。

无法继续时可标记 `blocked`，写清原因、已尝试步骤、所需决定或依赖及原状态；解决后回到原流程。
尚无远端时使用本地审查记录和合并 SHA；不能用“等待 CI”代替尚未配置的检查。

## 4. 多 AI 并行规则

- 独立写任务默认一个分支和 worktree；规则及示例见 [Git 规范](git-workflow.md)。
- 同一任务内，工具限制子代理共享目录时，Lead 可分配互不重叠路径，并独占共享文件和 Git 写操作、统一集成。本轮 M0 属于此例，不视为 worktree 隔离。
- Lead AI 先确定共享模型、输入输出、错误语义与版本；接口任务先验收，再并行实现使用方。
- 每个 Develop 只写任务卡允许的路径；发现必须修改共享文件时先交给该文件负责人协调。
- 文档研究、只读评审、无冲突模块可并行；任务互相依赖时按依赖顺序推进。
- 需要改变接口时，先提交影响说明和迁移方案；通知使用方并更新任务卡后再实施。
- Lead AI 负责集成顺序；不得在另一 Develop 尚在写入的工作区直接执行集成或清理。

## 5. 验收与交接

基础命令为 `PYTHONPATH=src python3 -m unittest discover -s tests -v` 和 `git diff --check`，在项目根目录执行；当前使用 `src` 布局且尚未安装包。
具体 CLI 演示及课程内容检查由任务卡补充；新增检查应覆盖真实行为或风险，不为每次文案调整机械添加测试。
交接至少包含：任务 ID、当前状态、分支/worktree、基线及交付 SHA、变更摘要、允许路径偏差。
同时提供：命令及环境、退出码和关键输出、样例输入输出、课程与评测版本、已知限制、遗留问题、回退方式。
附上人类 Lead 的需求审核记录及 Lead AI 的技术审核记录；标明待决定事项和下一位接手者。
学习复盘写明“学到了什么、为何这样设计、失败过什么、下个任务练习什么”，避免只汇报新增文件。

## 6. 课程与评估版本

- 课程内容、评分规则（rubric）、评测集与关键教学提示词各有显式版本及变更说明。
- 修改概念解释、案例假设、学习目标、分数阈值或迁移任务时，升级对应版本并列出影响。
- 每次评测记录代码 SHA、课程/rubric/评测集版本；接入模型后增加模型标识与配置。
- Develop 发现评分规则有问题，应保留原结果并提交修订建议，不能为让实现通过而自行放宽标准。
- 人类 Lead 审核学习目标、课程结论和评分含义；Lead AI 检查兼容性、覆盖和复现条件。
- 新规则须使用明确的新版本重新评测；保留旧结果及差异说明，不把不可比结果写成效果提升。
