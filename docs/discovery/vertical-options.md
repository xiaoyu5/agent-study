- 首门课程选择“概率与决策：贝叶斯思维”；第一节收窄为一次证据更新与基准率。

目标：从零理解 Agent 的核心机制，并逐步做出一个有人使用、结果可核验、失败可定位的垂直应用。先选具体重复任务，再围绕它设计工具和架构。

## 选择标准

- 有明确使用者和高频任务，能够描述输入与期望输出。
- 能获得一小组有代表性的资料，以及人工确认的正确结果。
- 任务需要根据观察选择下一步，而不只是执行固定转换。
- 能从小范围闭环开始，并逐步验证收益。
- 能解释错误后果，并定义适当的人工接管点。

固定规则足够解决的问题，应先做普通程序基线；只有需要澄清、检索、选择工具或迭代核实的部分才交给 Agent。

## 三个候选

| 方向 | 第一版范围 | 需要的数据 | 可评估的结果 | 主要学习内容 |
| --- | --- | --- | --- | --- |
| A. 单仓库测试失败诊断 | 一个指定仓库；读取失败日志与源码，输出原因假设、文件位置、证据和验证建议 | 可访问的代码及已知原因的失败案例；后续执行阶段需要可复现环境 | 原因定位、证据正确性、信息不足时的处理、耗时与调用成本 | 工具循环、代码检索、上下文、结构化输出、后续隔离执行 |
| B. 单产品安装故障工单辅助 | 一种产品、一类安装问题；分析工单，查版本文档，给出追问、回复草稿和转人工条件 | 脱敏工单、对应版本文档、可靠处理结果 | 引用正确性、必要追问、错误建议率、恰当转人工 | 知识检索、业务规则、澄清、证据约束、人工接管 |
| C. 订单与收款对账异常解释 | 两张约定格式的表；检查缺失、重复和金额不一致，输出可复算的异常报告 | 字段定义、关联键、明确规则与脱敏样本 | 计算正确性、漏报、误报、结果可复现性 | 工具契约、确定性计算、数据校验、业务解释 |

三个候选的初期产出分别是诊断报告、回复草稿和异常报告。A 在加入测试执行时须考虑代码执行隔离；B 需考虑知识版本与客户资料；C 的数值计算应交给确定性代码。具体边界随方向细化。

**条件性建议：**如果暂时没有专属业务数据，且希望深入学习开发工具与 Agent 机制，优先讨论 A。如果已有售后或运营场景及真实样本，优先围绕这些资料重新选题。这里的候选是工程判断，尚未经过用户需求或商业价值验证。

“本地资料起步”仅指资料和工具可以位于本地；是否使用远程模型、是否需要完全离线部署，仍需明确。

## 方向确定后的交付顺序

| 交付物 | 内容 |
| --- | --- |
| 产品范围与开发文档 | 用户故事、MVP 与非目标、输入输出、工具、失败行为和验收样本 |
| 架构与决策记录 | 模块边界、依赖方向、数据流、模型适配、状态及错误契约；解释选型原因 |
| Git 分支管理文档 | 主干策略、短期任务分支、命名、提交、PR、合并、回滚与 worktree 使用 |
| Lead/Develop 协作规范 | Lead 拆任务和定义接口；Develop 在授权范围实现；交接记录、评审与集成责任 |
| 学习开发路线 | 每个里程碑学习什么、实现什么、如何验证，并保留小练习与复盘 |
| 项目骨架 | 按选定语言建立最少模块、配置示例、CLI 入口和验证命令；首批任务可独立认领 |

Git 策略初步倾向 `main + 短期任务分支`，避免为学习项目提前引入复杂发布流程。`Develop` 是协作角色名，不自动意味着要建立长期 `develop` 分支。正式规范在团队形式明确后确定。

骨架设计优先考虑领域规则、运行循环、外部适配和入口之间的边界。初期使用模块化单体；根据确定的需求再决定是否需要数据库、Web UI、队列或多 Agent。
